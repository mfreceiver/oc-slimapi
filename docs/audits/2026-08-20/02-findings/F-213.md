## 证据
- messages.py:830-837：`lease = await registry.fetch_or_bypass(..., reserve_bytes=config.max_response_bytes)` → `async with lease:`（:837）内才 `async with pool:`（:862）——lease 的 caller ref（及其 budget 占用）跨越 admission 排队（最长 `transform_wait_seconds`=2s）+ offload 时长。
- 默认 `raw_fetch_max_bytes` = 64MiB = 单个 reserve（config.py:406-408、365）→ **整个 leased 预算同一时刻只容 1 个 flight**（CHANGELOG.md:283 已披露"默认容量下同时只有 1 个去重 flight，超额自动降级直取"）。
- joiner 复用同 entry（refs 共享，不额外占预算，singleflight.py:423-428）；**不同 key** 的新 caller 在此窗口 `fetch_or_bypass` 返回 None → bypass 直取（正确降级）。
- 佐证材料：03-reports/D05-concurrency.md §4.2 K2（持有图"lease→admission→offload"边）。
## 分析（机制、影响面、触发条件、可达性）
- 机制：lease-first 的内存上界模型（reserve 接管）与 admission-first（max_transforms×body）不同轨；lease 持续期 = 消费期（设计本意，questions.py:156-162 "budget ownership covers the caller's entire consumption"）+ **意外扩展的 admission 排队期**。默认预算下单 flight 独占 → 高并发列表请求的跨 key 去重大部分退化为直取（各自完整 GET）——与 1.5.0 去重目标的收益上限直接相关。
- 无死锁：持有图无环（§4 K2）；bypass 路径完备。
- 触发条件：coalesce_enabled + 任一列表/状态路由 lease 路径成功 + admission 有排队；不同 key 并发到达。
- 可达性：默认配置常态可达（max_transforms=1 使 admission 排队常见）。
