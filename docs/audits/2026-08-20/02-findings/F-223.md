## 证据
- hub.py:730-737：`rev = self._part_revisions.get(key, -1) + 1`；:735-736 `while len(self._part_revisions) > TOKEN_DISABLED_MAX(4096): popitem(last=False)`——活 part 的 revision 条目被 FIFO 逐出后，同 key 下一帧 `get(key,-1)+1 = 0` → revision 回退；
- 客户端契约（CRITICAL 1 docstring :2134-2147 自述）：ocdroid 对 `partEventRevision` 用严格 `>` 去重——回退帧被丢；
- 防线一：config.py:142-144 `assert TOKEN_LIVE_PARTS_MAX(32) <= TOKEN_DISABLED_MAX(4096)`——活跃 part（≤32）的条目因 LRU `move_to_end`（:732）热度不被逐出，**隐式跨模块不变量**；
- 防线二缺口：`apply_debug_budget_overrides`（hub.py:126-161）运行时改写三个模块全局，config.py:1033-1038 validate 只校验 `live_parts_max` 一项——误设 debug env 使 live_parts_max > 4096 时防线一静默失效。
## 分析（机制、影响面、触发性）
- 触发条件（生产）：需 >4096 个并发 revision 键——`_part_revisions` 键含 pending/迟到键，短暂高于 32 活跃 part 理论可能（大量短命 part  churn），概率低；`_retire_message`/`drop_part`/`_retire_session`/ttl_sweep 均同步清 revision（:942-943,:1942,:1164-1165,:1201），收敛路径齐全。
- 后果：单一 part 后续全帧被 ocdroid 严格 `>` 丢弃（静默流中断，客户端直到 resync/HTTP 对齐才恢复）。
