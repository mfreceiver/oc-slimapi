# F-212：absorb 重试失去 FIFO 排队位（TransformBusy 后重排队尾）——持续负载下重试者可被反复超越直至预算耗尽
- 严重度：P3
- 类别：risk（公平性退化；正确性不变）
- 位置：src/oc_slimapi/transform.py:236-245（wait_for 超时将 waiter 摘出队列）；重试循环 src/oc_slimapi/routes/messages.py:1205-1214（/full absorb）、:1573-1582（expand absorb）
- 置信度：medium-high（机制由 CPython 3.14 Semaphore FIFO + wait_for 摘除语义推得；无仓内测试锁定该 interleaving）
- 快照：0b836e7
- 状态：confirmed
## 证据
- transform.py:238-241：`await asyncio.wait_for(self._semaphore.acquire(), timeout=wait_seconds)`——超时路径取消 acquire 并从 Semaphore 的 waiter deque 摘除该 waiter（CPython `Semaphore.acquire` 的 `finally: self._waiters.remove(fut)`）。
- messages.py:1206-1214：`while True` 吸收循环——TransformBusy 后 `continue` → 下一轮 `pool.acquire(min(wait, remaining))` **重新排到 waiter 队列尾**；其间新到达的请求排在其前。
- 吸收预算默认 2.5s、单次等待上限 2s（config.py:640/364）：第一轮失败（~2s）后剩余 ~0.5s，任何在此窗口排队的新请求都先获得许可 → 重试者大概率再超时 → TransformBusy。
- 佐证材料：03-reports/D05-concurrency.md §2 T4。
## 分析（机制、影响面、触发条件、可达性）
- 机制：FIFO 公平只在**单次排队**内成立；absorb 的"摘除-重排"模式使其在持续到达流下处于结构性队尾。结果正确（最终要么获得要么 503，且 503 前零上游请求的不变量保持，messages.py:1200-1203 注释），但"吸收瞬态占用"的设计收益（transient slot occupancy 被吸收而非 503）在负载下退化为"等满预算仍 503"。
- 影响面：/full 与 expand 路由的客户端感知延迟（最长 2.5s 后 503 + Retry-After:2）；非 merged 列表路径无 absorb（单次 2s 等待）不适用本条。
- 触发条件：pool 饱和（max_transforms=1 默认下极易）+ 持续新请求流 + absorb 重试窗口内有竞争者到达。
## 契约/文档对照（规范轨引文）
- v3-contract 503 transform_busy 形状与 Retry-After 语义不变；本条是时延体验面（messages.py:1173-1179 docstring 所述"transient occupancy is absorbed"的收益边界）。
