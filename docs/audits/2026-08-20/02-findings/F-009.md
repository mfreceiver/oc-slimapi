# F-009：traffic snapshot 清理仅挂靠 access-log 维护循环——ACCESS_LOG_ENABLED=false 时快照目录无限增长且无告警
- 严重度：P2（A13 复核维持——默认双开的生产配置不触发，但触发路径两条且一条完全静默；磁盘无界增长 + snapshot 恒写放大）
- 类别：defect
- 位置：src/oc_slimapi/app.py:245-250,655-683,720-722；src/oc_slimapi/traffic_snapshot.py:79-101
- 置信度：high（A13 代码实证）
- 快照：0b836e7
- 状态：confirmed
## 证据
- app.py:668-674：snapshot prune 以 `functools.partial(prune_old_snapshots, …)` 绑为 access-log 维护循环的 `extra_prune`；
- app.py:655 `if access_log_active:`——**整个维护循环（含 extra_prune）** gated on access-log 实际安装结果；
- app.py:720-722：snapshotter 启动独立判断 `settings.traffic_snapshot_enabled and settings.traffic_metrics_enabled`——不依赖 access_log_active；
- app.py:245-250：`access_log_active = settings.access_log_enabled and not access_logger.disabled`；enabled-but-failed 路径有 warning（:246-249 "maintenance loop suppressed"），**explicit-false 路径零日志**；
- traffic_snapshot.py:79-101：`prune_old_snapshots` 无其他调用方（rg 全仓仅 app.py:670 partial 与 tests）。
## 分析（机制、影响面、触发条件、可达性）
- 机制：写路径与清路径挂不同开关——`OC_SLIMAPI_ACCESS_LOG_ENABLED=false`（或目录安装失败）+ snapshot 开（默认开）时，snapshotter 照常每 300s 落全量帧，prune 永不运行。
- 影响面：snapshot 目录无界增长（~300KB/天量级、永不压缩——operations.md §5.4 估算口径失效）；运维无信号（explicit-false 路径连 warning 都没有；enabled-but-failed 路径的 warning 只说 "maintenance loop suppressed"，未提示 snapshot 清理连带停摆）。
- 触发条件：① 显式 `ACCESS_LOG_ENABLED=false`（完全静默）；② handler 安装失败（有 warning 但语义不覆盖 snapshot）。
- 可达性：默认配置不触发（双开）；排障场景（手册 §6 建议临时关计量的是 `TRAFFIC_METRICS_ENABLED`——但运维若误关 ACCESS_LOG_ENABLED 即中招，两开关名称邻近且都默认 true）。
## 契约/文档对照（规范轨引文）
- traffic-accounting.md §6（:257）记载 snapshot retain 语义为「经 access-log 维护循环清理」，但未记载该挂靠的**前置条件**（access log 必须开且安装成功）；operations.md §5.3（:233）同款缺口。
