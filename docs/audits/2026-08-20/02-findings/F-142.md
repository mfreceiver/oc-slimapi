# F-142：proxy 终局边界两缝隙——域外方法（TRACE/CONNECT）得 Starlette 裸 405 非 coded 体；WS 501 为「accept 后 1011 close」非握手期 501
- 严重度：P3（初判，按 §3.3 决策表待 Phase 2/3 复核定级）
- 类别：contract（契约一致性缝隙，非行为错误）
- 位置：src/oc_slimapi/proxy.py:40-43（methods 列表）、proxy.py:34-38（WS stub）；state-machines.md 卡 2 D2-1/D2-2 种子
- 置信度：high（A3 代码事实核对，D03 §1.1/§1.3）
- 快照：0b836e7
- 状态：confirmed
## 证据
- proxy.py:41-43：catch-all `api_route` methods = [GET,HEAD,POST,PUT,PATCH,DELETE,OPTIONS]——TRACE/CONNECT 等不匹配 → Starlette 泛化 405，body 为默认非 `{"code":…}` 形状（errors.py 疑问 4 同源的结构性例外）。
- proxy.py:34-38：WS stub 先 `accept()`（握手 101 成功）→ `send_json({"code":"websocket_not_supported","status":501})` → `close(1011)`——`"status":501` 仅是 JSON 字段，客户端 HTTP 层看到的不是 501。
- tests/test_proxy.py:184-194 仅断言 WS 路由在挂，未钉 close code/呈现层级；test_terminal_matrix.py 未覆盖域外方法。
## 分析（机制、影响面、触发条件、可达性）
- 机制一（405）：契约 §8.1「错误体沿用 v2 全集」+ §8.3 优先链假定所有终局响应为 coded 体；域外方法落在 FastAPI 默认 405 形状（`{"detail":…}`），与「未收编路径 → 404 `{"code":…}`」的字面冻结并列成第三种错误形状。
- 机制二（WS 501）：501 语义按 HTTP 应在握手前拒绝；当前实现是应用层信令。ocdroid 侧如何消费（期待 1011？）未在 CLIENT_CHANGES/契约固化。
- 影响面：低——TRACE/CONNECT 在 stunnel/loopback 部署下罕见；WS 面本就仅存 stub。主要是契约完备性与客户端解析一致性。
- 触发条件：`curl -X TRACE` 任意路径；任意 WS upgrade。
## 契约/文档对照（规范轨引文）
- v3-contract §8.1/§8.2/§8.3（错误体全集与终局链）；§8.2-3.0.0「WebSocket 仍 501 stub」——未定义呈现层级与域外方法形状，两缝隙均无豁免条款。
