# F-361：release.sh 中途失败窗口——commit 先于 tag 校验/打 tag，失败残留 release commit 无回滚
- 严重度：P3
- 类别：quality(ops)
- 位置：scripts/release.sh:71-85（commit :73 → note 提取判空 :84 → `git tag -a` :85）
- 置信度：high（脚本逐行 + 失败序列推演，快照 0b836e7）
- 快照：0b836e7
- 状态：confirmed
## 证据
- scripts/release.sh:71-73：`git add pyproject.toml CHANGELOG.md` + `git commit -m "release: v${VERSION}"` —— **仓库已突变**。
- :76-84：tag note 经 awk 提取 CHANGELOG 目标节后 `[[ -s "$NOTE_FILE" ]] || { …; exit 1; }`——目标节**存在但内容为空**（:55 的 grep 只查标题行）时在此失败。
- :85：`git tag -a "$TAG" -F "$NOTE_FILE"`——脚本**无 tag 已存在预检**；重复发版同版本（如 pyproject 版本被人工回拨后 bump 撞旧 tag）时由 git 报错失败。
- 两处失败点均位于 commit 之后：仓库停留在「有 release commit、无 tag」的半发版态；脚本无 trap 回滚（trap 仅清临时文件 :77）。
## 分析（机制、影响面、触发条件、可达性）
- 机制：唯一一个「已突变仓库后才失败」的路径；其余全部失败点（参数/分支/脏树/门禁/解析/CHANGELOG 门禁/写回复核）均在首次写操作（:61 写回）前或写回后仍有 grep 复核兜底（:68）。
- 触发条件：① CHANGELOG 有 `## [X.Y.Z]` 标题但节体为空（异常人工操作）；② 目标 tag 已存在（人工回拨版本或同版本重发）。两者均属异常前置，概率低。
- 影响面：需人工 `git reset --hard HEAD~1`（并恢复 pyproject）才能重跑；若未察觉直接推送，origin 得到无 tag 的 release commit，违反 release.md §6「禁止拆开发版状态」。
- 缓解：不自动 push（:88-96）——半发版态不会自动外泄，人工 push 步骤是最后观察点。
## 契约/文档对照（规范轨引文）
- docs/release.md §3.2 第 5-8 步顺序（CHANGELOG 校验→写回→commit→tag）与脚本一致，规范本身未要求「先验后突变」——规范缺口同源；§6「禁止只 bump pyproject 而不打 tag（拆开发版状态）」正是本失败窗口会造成的态。
