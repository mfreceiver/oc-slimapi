# F-208：catalog 同 key straggler 排队超 1s grace 后重复刷新上游（refresh 不复查 lookup；默认 transform_wait_seconds=2s > grace 1s 使窗口现实可达）
- 严重度：P3
- 类别：defect（去重效率缝；无正确性影响）
- 位置：src/oc_slimapi/catalog_cache.py:106-135（`refresh`）；消费面 src/oc_slimapi/routes/_catalog_common.py:399（lookup 仅在 admission 前）、:422（refresh 在 admission 内）
- 置信度：high
- 快照：0b836e7
- 状态：confirmed
## 证据
- _catalog_common.py:399 `body = cache.lookup(key)` 在 `async with pool:`（:422）**之前**；miss 后排队 admission。
- catalog_cache.py:134 `body = await self._sf.fetch(("catalog-refresh", key), _fetch_and_store)`——单飞 key 的 grace = `_DEFAULT_RESULT_GRACE_SECONDS` = 1.0s（singleflight.py:97）；grace 过后同 key 新 caller 开新 flight（不做 lookup 复查）。
- 默认 `transform_wait_seconds`=2s（config.py:364）> 1s grace + `max_transforms`=1（:363）→ 同 key 第二个请求在 admission 队列等 >1s 后进入 refresh 时 leader 已完成且 grace 已过 → **第二次上游 GET**（同 body、缓存重存）。
- 佐证材料：03-reports/D05-concurrency.md §3 C2；01-explore/parts/e1-07 catalog 卡（机制核对）。
## 分析（机制、影响面、触发条件、可达性）
- 机制：双重防踩踏（admission 串行 + singleflight）在"排队时长 > grace"时出现缝：串行化本身把 straggler 推迟到 grace 窗外。响应字节/正确性零影响（同上游资源、TTL 正常）；损失 = 一次多余上游 GET + access log 多一行 miss（省流审计低估去重收益的方向）。
- 触发条件：同 key 并发 miss + admission 排队 >1s（pool 被大变换占用时常见）。
- 可达性：默认配置下真实可达（2s 等待上限 > 1s grace）；频度取决于并发与池占用。
