## 证据
- cap 判定 `total > max_bytes`（transform.py:189-190）作用在解码后累计值；cap-bail 时已缓冲 ≤ cap+64KiB（单 chunk 过冲）。
- upIn 口径：`on_read=stash_up_in`（各调用点）→ access 行/ledger 的 upIn=解压后字节。若上游对该请求回了 gzip（sidecar 隐式声明 accept-encoding，httpx 默认头），线上字节 < upIn——「省流」度量在 gzip 响应上系统性虚高（上游 /session 族是否真的回 gzip 未实机验证——上游服务端压缩行为未知，标注）。
- raw 透传族（providers v3/file×3/vcs×3/find/active/global-health/context）：无 pool 准入（_read_passthrough.py:119-134 `_maybe_pool(None)`），每请求缓冲上限=`max_response_bytes`=64MiB；并发界=共享 httpx 池 32 连接（upstream.py:44）⇒ 最坏瞬态 ~32×64MiB≈2GiB（config 域上限 256MiB 时 ~8GiB）。deploy MemoryMax=384M（oc-slimapi.service:70）使现实结局为 cgroup OOM-kill 自保护，而非主机内存耗尽——设计注释自认此兜底（:66-69）。
- pooled 族（messages/sessions/providers-v4/agent/command/…）准入先于 GET（`async with pool`，max_transforms=1 默认）不受此乘积影响。
## 分析（机制、影响面、触发条件、可达性）
- 机制：cap-on-decoded 是正确取向（限制 sidecar 实际负担）；代价是记账口径与 wire 脱钩 + 解码 CPU 无独立预算（上游 gzip 炸弹的解码 CPU 受 cap 早停约束，单请求解码量 ≤cap）。
- 影响面：①度量失真（traffic-accounting.md 全部分析口径）；②上游异常/恶意时 raw 族并发缓冲峰值的量化边界（有 cgroup 兜底，自伤式 DoS——重启即恢复，Restart=on-failure）。
- 触发条件：①上游对 sidecar GET 回 gzip 编码实体；②上游持续推送大实体 + 客户端并发打 raw 族路由。
- 可达性：①取决于上游行为（半可信）；②三入口均可但收益为纯自扰。
