## 分析（机制、影响面、触发条件、可达性）
- 机制：`on_upstream_reconnect()`（或收尾段任何）抛常规异常 → task 以 exception 终止但**未被 await/观察**（`_removal_task` 仍指向它）→ ① "Task exception was never retrieved" GC 告警噪音；② `_global` 未置 None、hub 4 task 已被 cancel → 该 GlobalHub 处于半拆状态；③ 后续每次 last-detach 的 `maybe_arm_grace_if_idle` 被 :183-184 挡住 → **B-D1 修复的"token-only 消费者离开后 hub 永活/上游连接泄漏"全面回归**，且一旦发生不可自愈（无任何路径清 `_removal_task`，除 `close()`）。
- 影响面分级：**运行期长进程为主要影响面**（生产常态：idle↔active 多轮循环，每轮一次触发机会）；进程关停时 `close()`（registry.py:400-402）会 cancel + 置 None 残留 task，兜底收敛——故部署上最坏结果是"运行期连接/内存泄漏 + 告警"，非关停破坏。
- 触发条件：`on_upstream_reconnect` 抛错（当前实现 tokenstream/hub.py 内部清态，未见已知抛错点——防御性缺口）或未来该段新增代码抛错。
- 可达性：低概率 × 高影响 + **不可自愈**（一次性损坏后 grace 机制永久失效直到进程重启）。
## 契约/文档对照（规范轨引文）
- 无直接 wire 面（连接生命周期内部）；受影响的是 T3/SSE 资源收敛不变量（design §5.2/§16-B、B-D1 修复声明），与 v3-contract §5 SSE 服务的可用性间接相关——修复属实现自由，不动契约。
## 复核记录（Phase 3）
- **终态 confirmed / P2**。锚点抽查（2026-08-20）：registry.py:183-184 `if self._removal_task is not None: return` 命中——task 异常终止后引用残留 → arming 永久 no-op 的机制成立；`_remove_hub_after_grace` sleep 后收尾段无 `except Exception`（:322 `on_upstream_reconnect()` 无守卫、:324-325 清引用在异常时不执行）。除 `close()` 外无清理 `_removal_task` 的路径（A5 已核）。原状态行括注「A5/D05 Phase 2 填充分析」由本节承接。
## 建议方向（非实现）
